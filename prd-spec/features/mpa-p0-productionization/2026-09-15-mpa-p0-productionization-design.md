## 1. Conclusion and boundary

AgentKit Studio becomes the sole MPA management entry, and `agentkit-mpa-agent` is the execution Runtime. P0 does not develop or depend on the Managed Agent product, its CRUD APIs, its release versions, or its Session API. Studio reuses its existing Agent creation form and resource selectors as the authoring surface, normalizes the submitted configuration into an immutable MPA Profile revision, and applies that Profile directly to mpa-agent. The MPA Agent detail page is the unified place to view Profile status, apply or reapply the Agent-level Profile, manage Session execution configuration, inspect diagnostics, and delete the Runtime. It must not send MPA users to the generic Runtime update capability path when that path depends on `/list-apps` and cannot represent an A2A-only mpa-agent Runtime. mpa-agent does not build a template center, expert marketplace, review/install workflow, or a separate publishing product. `arkclaw-team` is read-only functional reference material, not a new-path dependency; none of its historical users, sessions, templates, credentials, IDs, or run records are migrated.

P0 delivers the core path: create/update an MPA Agent, prepare a Runtime, apply the Profile, create a Session, execute chat and workers, manage session execution configuration, pause/resume/continue, retrieve history, diagnose with Debug/Trace, and update or recover the Runtime. Scheduled tasks, Feishu integration, website integration, Resource Library, and global Search are deferred.

| System | Sole responsibility | Explicit exclusion |
| --- | --- | --- |
| AgentKit platform | Existing Studio creation surface; Skill/Tool/Environment/Vault and other platform resources; Runtime lifecycle; account authorization | P0 does not add or depend on Managed Agent CRUD/version/Session |
| VeADK Studio/BFF | Validate the existing Agent draft, normalize an MPA Profile revision, orchestrate Runtime/Profile application, and present status | Does not create a second platform product or drive workers directly |
| `agentkit-mpa-agent` | Executable Profile projection, Session/Turn, resource resolution, worker orchestration, execution control, diagnostics | No template/expert/review-install or independent Agent-version product |
| `mpa-codex-worker` | Existing isolated execution protocol | No change unless a tested protocol gap is demonstrated |
| `arkclaw-team` | Read-only functional reference | No dependency, dual-write, migration, or old-ID/API compatibility |

## 3. User scenarios and requirements

### Scenario A: create and first-run an MPA Agent

**Given** a user creates an Agent in AgentKit Studio and selects the MPA Runtime type.

**When** Studio validates the Agent draft, creates an immutable MPA Profile revision, prepares or reuses its Tool and Runtime, and applies that Profile to the Runtime.

**Then** the UI shows one staged creation operation; it reports “runnable” only after Profile application and an execution-ready smoke pass, after which the user can create a Session and receive the first streaming result.

### Scenario B: update an Agent Profile

**Given** the applied MPA Profile is at revision N.

**When** the user saves changes to Model, System, Tools, Skills, MCP, or Multiagent.

**Then** Studio submits the new digest with the current ETag and a stable idempotency key. Runtime atomically allocates revision N+1. The same key/digest returns the original revision, the same key with a different digest returns `409 idempotency_mismatch`, and a stale ETag returns `412 profile_changed`.

### Scenario C: edit session execution configuration

**Given** a Session is at execution configuration version 6, composed from Agent defaults plus Session overrides.

**When** browser A changes the model to M2 while browser B attempts a Skill change against version 6.

**Then** A creates version 7; B receives `412 execution_config_changed` with current version 7 and cannot overwrite A. An already-running Turn continues with its recorded version 6; the next Turn uses version 7.

A “session execution configuration version” is a monotonically revisioned runtime record of one Session's execution choices, not a copy of platform resources. For example, it records `skillId=s-1, version=3`, `environmentId=e-2, version=5`, and a model override, while AgentKit continues to own Skill content and Environment secrets. On Turn start, the accepted version and resolved result are recorded so an in-flight Turn cannot be changed by later edits.

### Scenario D: pause, resume, and timed-out continuation

**Given** a Turn has a primary executor and two workers.

**When** the user pauses.

**Then** it becomes `paused` only after every active participant reaches a safe point; partial acknowledgement remains `pausing` or ends in a classified timeout. Resume continues the same Turn within 300 seconds while its lease is viable. Past the boundary or when unrecoverable, only an explicit user action causes the Runtime to atomically create a linked new Turn.

### Scenario E: refresh and failure recovery

**Given** a request fails after its execution record is committed but before dispatch, or the browser refreshes during streaming.

**When** the client retries with the same idempotency key or reconnects with an event cursor.

**Then** the Runtime returns the original invocation/result and resumes at the cursor without a duplicate Turn, event, artifact, or usage increment.

## 4. Core design

### 4.1 Wiring the Studio MPA Profile to the Runtime

Create/update is a Studio-to-Runtime operation:

1. The browser submits the existing Studio Agent draft to VeADK BFF. No Managed Agent API is called.
2. BFF validates resource references and normalizes the accepted draft into `sourceProfileId + profileDigest`. It does not allocate a revision and must not forward unchecked browser fields.
3. BFF calls mpa-agent Profile apply. The Runtime validates version, references, and permission before writing a new `mpa_agents` revision.
4. BFF queries apply status. Failure preserves the last applied MPA Profile revision and a retryable operation; it does not report the MPA Agent as runnable.
5. A new Session pins the selected Profile revision at creation. An active Turn never hot-switches.

The BFF reuses existing Studio draft parsing and AgentKit resource clients. It adds a typed mpa-agent Profile client rather than a Managed Agent OpenTOP adapter. Runtime allocates the unique `profileRevision` inside the successful ETag/CAS transaction and returns it; BFF never preallocates a revision. A conflict returns `409 profile_version_conflict` plus current revision and never overwrites automatically.

P0 does not introduce a self-signed assertion service. Studio already holds a middleware-validated user bearer token in OAuth/gateway mode, and AgentKit Runtime custom JWT authorization validates the same issuer/client. BFF forwards only that validated bearer token. mpa-agent projects REST bearer JWT and A2A TIP into one `RuntimePrincipal` and applies business-scope authorization on new writes. The implemented S4-06 Runtime slice adds a shared `RuntimePrincipalAuthorizer` seam and rechecks the current grant before `/run`, resume, `/continue`, model/workload TIP or API-key resolution, sandbox run credential preparation, and tool dispatch. Runtime carries only a normalized, non-secret principal snapshot across accepted Turn/inbox recovery; it never stores the bearer token. Local claim/rejection and fake-revocation contracts gate S1/S4-06; issuer, audience/client, TTL, JWKS rotation, real revocation lookup, and one authorized Profile apply/status request remain mandatory deployed-environment release gates. Neither phase may fall back to browser headers, Runtime keys, or disabled JWT.

| Studio AgentDraft field | Runtime field/behavior | Mapping rule |
| --- | --- | --- |
| Studio draft ID | `sourceProfileId` | Stable source identity for audit and idempotency; not a Managed Agent ID |
| `Name`, `Description` | `name`, `description` | Copy and validate length |
| `System` | `agentsMd` | Runtime instruction body; retain a source digest |
| `Model.Id` | `model` | Trim; reject provider URLs or credentials |
| `Tools[]` | `tools[]` | Retain type/name/enabled/permission policy; unsupported types return `422 unsupported_profile_field` |
| `Skills[]` | `skills[]` | Pin `SkillId + Version`; BFF resolves omitted versions first |
| `MCPServers[]` | `mcp` | Map to ID allowlists/scoped grants; pass only secret references |
| `Multiagent` | Runtime subagent configuration | Preserve roles, Agent references, and versions; unsupported shapes fail explicitly |
| `Metadata`, `Tags` | `metadata` | Allowlist non-secret keys; classification remains `veadk:agent-type=mpa` |
| Managed Agent-specific fields | Not accepted | Managed Agent CRUD/version/Session is outside P0; MPA Session overrides are owned by runtime `session_execution_configs` |

Minimal Profile apply request:

```json
{
  "sourceProfileId": "studio-agent-example",
  "sourceProfileDigest": "sha256:example",
  "profile": {
    "name": "Research Agent",
    "system": "...",
    "model": {"id": "model-example"},
    "tools": [],
    "skills": [{"skillId": "s-example", "version": "3"}],

    "multiagent": null,
    "metadata": {}

```

First apply carries only `If-None-Match: *`; an existing projection carries only `If-Match: "<runtimeRevision>"`. They are mutually exclusive. Successful apply/status responses carry `profileRevision` and `ETag: "<runtimeRevision>"`. The same operation key/digest is a successful replay, the same key with another digest returns `409 idempotency_mismatch`, and stale ETag returns `412 profile_changed`.

BFF persists an MPA lifecycle operation before Runtime creation/Profile apply under `veadk-studio/v4/users/{principal}/mpa-agent-operations/{operationId}.json`, using TOS `forbid_overwrite` creation and ETag conditional updates. Create and update require a client-persisted `Idempotency-Key`; BFF uniquely creates by `principal + operationKind + mpaInstanceId/createIntent + key + requestHash`, and both endpoints return `202 + operationId`. The same request returns the original operation; changed content conflicts. `GET /web/mpa/agent-operations?status=active` recovers a lost first response. Creation is `runtime_preparing -> profile_applying -> smoke_running -> runnable`; update is `profile_applying -> succeeded`; both may enter `failed_retryable|failed_terminal`. It stores MPA instance ID, from/target Profile revisions, Profile digest, Runtime ID, Profile operation ID, stage, retry count, safe error, and timestamps, never credentials. Recovery reconciles Runtime binding plus Profile status and resumes from the last safe stage instead of repeating a write.

Local Studio development may use a process-local operation repository only when `veadk studio --dev` is active and Studio TOS is not configured. This keeps local Profile apply and retry flows testable against a real Runtime while preserving the same operation ID, request-hash idempotency, and ETag compare-and-swap semantics. It is not durable and is not release evidence; non-dev deployments still require Studio TOS and fail Profile write routes with `mpa_operation_service_unavailable` when storage is absent.

### 4.3 Idempotency, errors, and performance

Profile apply, profile-upgrade, and continuation use `runtime_operations` where a reusable async status/replay envelope is needed, unique by `principal + operation + target + Idempotency-Key`, retaining canonical request hash, response snapshot, resource IDs, and a 24-hour expiry. Run acceptance uses `turn_execution_records` as its dedicated Turn ledger because the durable replay value is the accepted `turnId/invocationId/operationId` plus the frozen execution configuration. execution-config PATCH uses only revision/ETag CAS; pause/resume uses only `a2a_task_controls` generation, request hash, and replay result, without duplicate ledger writes. Same key/hash returns the original result; same key/different hash returns `409 idempotency_mismatch`. A pending Profile never becomes the current `mpa_agents` revision; only a success transaction switches the applied revision. Run and continuation write `turn_execution_records` plus a dispatch intent in one transaction, followed by an idempotent dispatcher. The contract does not promise distributed ACID with external AgentKit or the A2A SDK TaskStore.

The common error shape is `error.code/message/requestId/retryable/currentState`. Key codes are `profile_version_conflict`, `execution_config_changed`, `session_busy`, `unsupported_profile_field`, `resource_unavailable`, `idempotency_mismatch`, and `not_execution_ready`. Existing endpoint envelopes change only after capability-version negotiation.

MPA deletion is intentionally not a new distributed transaction. The preview and execution both recompute current blockers from server-side state. Active operation and active Session blockers are authoritative at execution time, so a stale browser preview cannot force deletion. A repeated delete after one Session has already been removed treats that Session's `404` as already cleaned and continues with the remaining stages; deleting the AgentKit Runtime remains the final platform side effect. Current preview scope is the target Runtime API visible to the authorized caller, not a cross-user global Session index.

| Operation | P0 server-side target (caller network excluded) | Constraint |
| --- | --- | --- |
| Profile apply acceptance/replay | p95 <= 500 ms | Validate IDs, version, digest, and permission synchronously; resolve remote detail asynchronously |
| Session execution-config GET/PATCH | p95 <= 300 ms | One transaction; do not hold a database lock during remote resource fetch |
| Run acceptance | p95 <= 500 ms | Return accepted/operation ID without waiting for model completion |
| Pause/resume/continue acceptance | p95 <= 500 ms | Return target state; participant convergence is observed asynchronously |
| First SSE event | p95 <= 2 s | Warm Runtime; excludes model first-token SLA |
| List/detail | p95 <= 1 s | Server pagination, default 20/max 100; no N+1 Runtime/resource scan |
| MPA delete preview | p95 <= 1 s | One Runtime binding/profile lookup and one bounded Runtime Session list; no cross-region scan when `runtimeId` is supplied |

Performance is measured after five warm-up requests over at least 100 requests, concurrency 10, a fixed 20-item list, and same-region networking. Reports include p50/p95/max, error rate, and tested revision. Model first-token and Runtime cold-start latency are reported separately and do not count as API-acceptance latency. Until run, these are targets, not passing evidence.

### 4.4 State machines

Runtime operation: `accepted -> running -> succeeded | failed_retryable | failed_terminal`. Profile apply currently completes synchronously after acceptance, so it normally transitions directly from `accepted` to `succeeded` or `failed_terminal`; its public Profile result remains `status=applied` on success. A `failed_retryable` operation may return to `running`; terminal states cannot move to another terminal outcome. State updates use compare-and-swap so concurrent completions cannot overwrite each other.

Runtime readiness: `prepared -> resource_created -> transport_ready -> profile_applied -> execution_ready -> verified`, with `failed_retryable` or `failed_terminal` reachable from each stage. The UI reports “created and runnable” only at `verified`.

Turn: `queued -> running -> pausing -> paused -> resuming -> running -> completed|failed|cancelled`. Partial participant acknowledgement remains `pausing`; an ACK from an old generation is ignored. The implemented S4-02 Runtime slice wires the existing control API, A2A primary executor, and Codex worker interruption path through `ParticipantBarrierService`: pause creates the next participant generation, the task becomes `paused` only after every current-generation active participant has acknowledged a safe point, late workers that start after the task is already `paused` still receive pause and ACK the current generation before resume, and completed/failed/cancelled workers are marked terminal so they do not block later pauses. The implemented S4-03 slice keeps same-Turn resume valid at the exact 300-second boundary when the task owner lease is still viable, returns `new_turn_required` when the pause is older than 300 seconds, when the task owner lease is lost, or when a participant is `lost|failed`, and keeps same-key `new_turn_required` retries idempotent. Resume returns the aggregate task to `running` and seeds the next participant generation from the previous paused generation. The implemented S4-04 Runtime slice exposes `POST /api/v1/a2a/tasks/{taskId}/continue`: after `new_turn_required`, it uses the old task invocation to find the previous business Turn, writes a new `turn_execution_records` row with `continuation_of=<oldTurnId>`, reuses the frozen execution-config snapshot and dispatch payload, closes the old active dispatch row, and schedules the existing inbox/outbox worker. The implemented S4-05 Studio slice removes the prompt-based continuation fallback: when resume returns `new_turn_required`, Studio calls Runtime `/continue`, then subscribes to Runtime `/sse` with the returned `invocationId` and existing `lastEventId`, without issuing an ordinary `/run` or fabricating a prompt. The implemented S4-06 Runtime slice rechecks the current RuntimePrincipal grant before accepting run/resume/continue side effects and before background secret/tool effects. If the injected authorizer reports a revoked grant, resume and continue return `403 runtime_action_forbidden` before state mutation or continuation acceptance, and accepted inbox execution fails before model TIP, workload TIP, OpenViking API key, sandbox run credentials, or sandbox/tool dispatch are used. The implemented S4-07 browser gate verifies the end-to-end Studio loopback behavior: partial worker acknowledgement remains `pausing`, all participants reaching safe points exposes resume, same-Turn resume returns to `running`, an interrupted task with `resumeDisposition=new_turn_required` is shown as a user-readable checkpoint continuation state, browser refresh does not auto-create a continuation, and only an explicit click calls Runtime `/continue` followed by `/sse`.

Session execution configuration has no separate business status: every successful PATCH creates a monotonic revision. Validation failure creates no revision and returns invalid references; a Turn's accepted revision is immutable.

Session Profile upgrade shares the configuration revision but must use its dedicated API. The target Profile becomes the new base, explicit override/clear values are retained, inherit categories take target defaults, and effective references are recomputed. Any missing, revoked, or incompatible resource rejects the entire operation before the transaction; the old revision remains intact and no non-executable revision is created. One success transaction updates `session_meta.profile_revision/execution_config_revision`. Same key/hash returns the same new revision; concurrent ETag change returns `412`.

Delete state machine: `preview -> blocked | ready -> cleaning_sessions -> deleting_runtime -> deleted | failed_retryable`. `blocked` is returned before any mutation when the MPA operation store has an active create/update operation, when the Runtime binding is missing or ambiguous, when the Runtime Profile is orphaned, or when Runtime Sessions are in `queued|running|pausing|paused|resuming`. `cleaning_sessions` deletes only visible idle/terminal Runtime Sessions and treats a per-session `404` as already cleaned. `deleting_runtime` calls the AgentKit Runtime delete API only after the Runtime-side cleanup stage succeeds.

## 5. Data model

### 5.1 Reuse rules

- Studio is the authoring authority for the accepted MPA Profile; mpa-agent `mpa_agents` persists immutable executable revisions. Do not add Managed Agent, template, expert, review/install, or publishing-version tables.
- AgentKit remains authoritative for Skill, Tool, Environment, Vault, and Resource. Runtime stores only IDs, pinned versions, digests, and secret references.
- Do not modify AgentKit-owned tables, migrate ArkClaw tables, or create old-ID mappings.
- New columns are additive; every new store has PostgreSQL and in-memory implementations.

Ordered migration is `runtime_operations -> additive mpa_agents/mpa_meta/session_meta columns -> session_execution_configs -> turn_execution_records -> a2a_turn_participants -> secret reference columns/indexes -> remaining indexes/constraints`, with a persisted schema version. Deploy schema expansion first, then dual-version-readable code, then enable new writes; reject rollback whenever old code cannot safely read new state. AgentKit mode rejects new plaintext `agent_api_key/model_api_key` writes and converts/clears any existing new-platform values into protected references. S5-01a also registers legacy plaintext values read during migration in a process-local value-aware redaction registry before any provider call or diagnostic emission. API access logs, client-visible Session output, Runtime Console responses, lifecycle details, trace persistence, and `runtime_operations.response_snapshot/resource_ids` pass through the same redaction boundary. Runtime operation status responses omit principal, idempotency key, and request hash.

## 9. Review conclusion and confirmed product decisions

This `review-spec` revision resolves the blockers: duplicate template/expert/version ownership, unclear authority, underspecified API parameters/idempotency, ambiguous “resource snapshot” language, and frontend-created continuation. Anything confirmable from code or read-only execution is now a conclusion rather than a question.

The user confirmed both product semantics as binding design decisions on 2026-09-15:

### D-1: an existing Session adopts a new Profile only after explicit upgrade

- **Confirmed option A: an existing Session pins the MPA Profile revision selected at creation; a newer revision takes effect on the next Turn only after an explicit “upgrade session” action.**
- Studio must show “new version available,” current/target versions, and an upgrade action. Session behavior is unchanged before upgrade.
- An active Turn never switches versions. Upgrade uses CAS and an idempotency key; failure retains the original version.
- Automatic latest-version tracking and per-Agent tracking policy are excluded to prevent silent model, tool, or instruction changes within one Session.

### D-2: an Agent is runnable only after the complete execution path passes

- **Confirmed option A: after Studio accepts MPA creation, show “deploying”; show “runnable” only after Runtime, Profile application, and execution-ready smoke all pass.**
- Creation returns a staged operation that can be queried after refresh. Failure shows safe resource IDs, the failed stage, and a retry action.
- When the MPA operation exists but Runtime is not executable, the UI cannot report creation success or start a conversation.
- Synchronous long polling and “Agent persisted means success” are excluded to avoid unrecoverable timeout UX and entry into a non-executable Agent.

## 10. Risks and rollback

- Local bearer/TIP claim mapping and rejection paths must pass in M0. The deployed `S5-14` release gate proves issuer, audience/client, JWKS rotation, revocation, and authorized Profile apply/status. Failure blocks release, not local S1 TDD. BFF forwards a validated bearer unchanged and issues no new assertion; never trust browser owner headers, Runtime keys, or the old service.
- Studio operation persistence and Runtime Profile apply are not a distributed transaction. Converge with an operation plus idempotent apply; preserve the last applied Profile revision and show “not applied” on failure rather than claiming runnable.
- Remote resources referenced by a session execution configuration can disappear after commit. Revalidate version and permission before Turn dispatch/materialization and fail before a side effect.
- Runtime database migration is additive. Check old/new schema and worker protocol compatibility before rollback; reject an incompatible downgrade before mutation.
- Delete affects only current MPA Runtime/Profile data, checks active Sessions and shared resources, and performs staged cleanup. It never touches historical ArkClaw data or Managed Agent data.
