# PRD 与设计规格规范

[English](README.md)

本目录存放 VeADK 针对具体变更的需求和方案设计。目录组织参考 `mpa-codex-worker` 的功能、重构、Bug 修复分类，同时采用 VeADK 自身的组件边界、工具链和双语文档约定。

## 1. 文档职责

| 位置 | 职责 |
| --- | --- |
| [AGENTS.md](../AGENTS.md) | 仓库级开发流程和强制门禁，使用英文编写。 |
| `prd-spec/` | 某次变更的原因、范围、方案、实施任务和验收标准。 |
| [specs/](../specs/README.zh.md) | 持续维护的组件契约：职责、接口、状态、数据和失败语义。 |
| [frontend/SPEC.md](../frontend/SPEC.md) | 现有 Studio 前端及配套后端开发规范，不在此重复或替换。 |
| `docs/content/docs/`、模块 README 和 `examples/` | 用户文档和可运行的使用示例，保持各区域已有的语言约定。 |

PRD 描述一次变更，组件 spec 描述持续维护的契约。两者相互关联，但不建立相互竞争的契约副本。

## 2. 目录结构与命名

```text
prd-spec/
├── README.md
├── README.zh.md
├── features/
│   └── <topic>/
│       ├── YYYY-MM-DD-<description>.md
│       └── YYYY-MM-DD-<description>.zh.md
├── refactors/
│   └── <topic>/
│       ├── YYYY-MM-DD-<description>.md
│       └── YYYY-MM-DD-<description>.zh.md
└── bugfixes/
    └── <topic>/
        ├── YYYY-MM-DD-<description>.md
        └── YYYY-MM-DD-<description>.zh.md
```

- 首份实际设计需要时再创建分类和主题目录，不要求空目录骨架或占位设计。
- 主题名和描述采用稳定的英文 kebab-case；日期为设计创建日期。
- 英文使用 `.md`，中文使用 `.zh.md`。两份文件的目录、日期和基础文件名一致。
- 例如 `features/runtime-session-lifecycle/2026-09-10-runtime-session-lifecycle-design.md` 及其 `.zh.md` 对应文件仅演示命名，不代表已实现该功能。
- 使用主题作为稳定的 change ID。后续独立变更复用同一主题时，应分配不同的 change ID 并关联前一版设计。
- 实质性设计迭代新增带日期的双语文件；同一天多次迭代时增加可区分的英文后缀。保留历史设计并链接后继版本。
- 勘误、评审整改、翻译和实施状态更新可直接修改当前双语文件。不得通过改写旧设计掩盖决策变化。

## 3. 分类规则

| 类别 | 适用范围 |
| --- | --- |
| `features/` | 新增用户可感知或公开 SDK 能力，包括对已有行为的扩展。 |
| `refactors/` | 保持外部行为和契约不变的内部结构调整。 |
| `bugfixes/` | 修复已有缺陷、回归、崩溃、数据错误或交互故障。 |

根据预期结果而不是 diff 大小选择分类。不得以重构名义隐藏公开行为变化。混合或不明确的范围应在实现前澄清。

## 4. 双语契约

1. 每份设计包含一份完整英文文档和一份完整中文文档。每种语言内部不拆分为独立 PRD、spec、plan 文件；需求、设计、任务和验收标准保持在同一文件中。
2. 每份文件顶部附近提供对应语言版本的相对链接。
3. 两版的 change ID、修订日期、生命周期状态、需求 ID、任务 ID、验收 ID、API 标识符、路径、命令、示例和数值限制必须一致。翻译正文，不翻译程序标识符。
4. 同一次变更同步维护两版。中文版不是缩略摘要，英文版也不是可延后的翻译任务。
5. 评审必须检查语义等价。缺少对应版本、翻译过期或需求冲突会阻塞设计批准和交付；不得静默选用对当前实现更方便的版本。
6. 本仓库双语规则覆盖通用 PRD skill 的“仅中文”默认要求，但不改变文档站 `.mdx` / `.en.mdx` 的约定。

## 5. 设计必需内容

每份文档必须能脱离聊天记录独立理解。可以引用代码和契约，但关键决策及验收条件必须在文档中明确说明。

| 章节 | 必需内容 |
| --- | --- |
| 元信息 | Change ID、创建及修订日期、生命周期状态、对应语言链接、相关组件 spec，以及适用时的前序和后继版本。 |
| 背景与证据 | 当前行为、受影响用户或调用方、具体源码或复现证据，以及尚未验证的假设。 |
| 目标与非目标 | 本次变更必须实现的结果，以及明确不在范围内的内容。 |
| 场景与需求 | 可观察的 Given/When/Then 场景及稳定的 `FR-*` 需求 ID，包括失败和边界情况。 |
| 设计与契约影响 | 职责、备选方案及选择、接口、状态和数据、并发、权限、安全、兼容性及受影响调用方。不适用的部分注明原因。 |
| 实施任务 | 有序的 `T-*` 任务、涉及文件、依赖关系，以及关联的需求和测试。 |
| 验证与验收 | `AC-*` 验收标准、测试层次、仓库实际命令、所需环境、反向用例及完成判定所需证据。 |
| 风险与待决事项 | 未解决决策、运行风险、发布和恢复注意事项，以及明确约定的后续工作。 |
| 评审与交付记录 | 评审问题和处理结果、用户批准、已执行检查及结果、跳过或阻塞检查及原因、剩余范围。 |

生命周期状态使用 `draft`、`in-review`、`approved`、`implemented` 和 `superseded`。批准要求阻塞项清零并获得用户同意；`implemented` 还要求范围内任务完成且具备验收证据。不得将设计获批等同于功能已交付。

### 功能文档重点

说明用户或 SDK 调用方的流程、新行为、接口示例、依赖、错误，以及如何通过实际入口使用该能力。跨越运行时或 UI 边界时，包含集成和端到端验证。

### Bug 修复文档重点

记录预期与实际行为、复现条件、根因证据、受影响路径，以及修复前会失败的回归测试。区分假设与已确认原因。说明方案为何解决根因，而不是掩盖现象。

### 重构文档重点

说明现有耦合或复杂度、新职责边界、保持不变的外部契约、实施顺序及证明行为等价的测试。明确必要的数据或调用方切换；公开行为发生变化时，应重新考虑分类。

## 6. VeADK 影响检查表

只展开受影响的领域；当某个相关契约可能受到影响但实际被排除时，应说明理由。

- **Python SDK：** 公开导入和签名、Agent/Runner 行为、配置及默认值、可选依赖、支持的 Python 版本、示例和下游调用方。
- **Studio 与代码生成：** 前端类型、服务端路由、生成的 Python/配置/依赖、部署 Payload、构建后的 Web 资源，以及 `frontend/SPEC.md` 的规范。
- **运行时与集成：** Session 身份和持久化、流终止、取消、重试、迟到事件、MCP/工具、Harness/Sidecar 行为及资源清理。
- **云与安全：** Provider/区域边界、授权、凭据、用户控制的 URL/文件、脱敏、外部副作用及部分失败后的恢复。
- **用户文档：** 受影响的中英文页面、示例 README，以及是否需要升级或迁移说明。

不得照搬 `mpa-codex-worker` 专用命令、凭据、部署授权、覆盖率阈值，或一刀切的“不保留兼容”策略。VeADK 既是已发布 SDK，也包含 Studio；破坏性变更必须明确评估影响并获得批准。

## 7. 从设计到交付的流程

1. 检查当前实现及相关契约，澄清范围，在修改前就方案取得一致。
2. 编写双语 PRD 并评估组件 spec 影响。创建或更新受影响组件的双语 spec；无影响时在 PRD 中说明理由。
3. 评审需求、契约一致性、实现可行性、测试及双语等价性。在修改生产代码或测试前清零阻塞项并记录批准。
4. 按已批准任务进行规格驱动开发和测试优先实现。需求变化时，先返回设计评审，再继续实现该变化。
5. 先运行针对性检查，再执行 `AGENTS.md`、`frontend/SPEC.md` 和受影响 CI 工作流要求的门禁。UI 变更必须进行真实浏览器验证；Mock 或静态检查不能证明真实集成行为。
6. 审查实现和测试，解决阻塞问题，并将两种语言的文档与交付行为对齐。记录实际命令、结果和缺失的验证。
7. 只有约定任务和验收标准全部满足后才能标记为已实现。延后范围必须获得用户明确同意并建立可追踪的后续任务，不得静默变更状态。

不改变运行时行为或公开契约的纯文档、翻译或格式调整，无需递归编写“关于文档的 PRD”。仍须确认范围、同步适用的双语文件，并执行相关检查。

## 8. 验收追踪

每份设计使用紧凑表格，并随实现补充证据：

| 需求 | 任务 | 验收标准 | 测试或验证命令 | 结果/证据 |
| --- | --- | --- | --- | --- |
| `FR-1` | `T-1` | `AC-1`：可观察结果 | 精确命令或人工操作步骤 | 执行前为 `not_run` |

检查状态使用 `pass`、`fail`、`blocked`、`not_run` 或 `not_applicable`，后三种必须说明原因。记录执行日期、被测版本/diff 范围和简要结果。默认将证据保留在设计内；确需独立产物时链接到产物，不强制新增多层报告目录。

两种语言的文档和证据均不得包含真实 API Key、AK/SK、Token、Cookie、签名 URL、个人数据或未脱敏生产日志。
