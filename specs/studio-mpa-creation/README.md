## Responsibility and boundaries

VeADK owns managed YAML parsing, cloud/database orchestration, authorized durable creation tasks and the MPA directory dialog. No external source checkout is required. Shared registry/bootstrap contracts remain interoperable with the MPA image. Legacy `veadk mpa create` remains separate and unchanged. Model execution and channel routing remain Runtime responsibilities. Managed runtime IAM preparation follows the contract below.

## Contracts

- **CON-15 — Studio Identity reuse:** A cloud Studio deployment saves its UserPool name, client name, Identity region, and public MPA callback in four `VEADK_STUDIO_MPA_*` function environment values during the second release. Managed profile loading uses this complete server-owned set when the built-in Studio profile omits Identity values, rejects partial sets and explicit mismatches (including `managed.runtime.env`) before cloud writes, and passes the resolved values to the fixed runner. Without this set, standalone CLI/YAML behavior is unchanged. The new Runtime receives `MPA_USER_POOL_NAME`, `MPA_USER_POOL_CLIENT_NAME`, `IDENTITY_CALLBACK_URL`, and `IDENTITY_REGION`; browser requests and task persistence contain none of them. Existing Studio deployments require redeployment, and existing MPA Runtimes are unchanged. See [Identity reuse design](../../prd-spec/features/studio-mpa-identity-reuse/2026-09-23-deploy-identity-reuse.md).

- **CON-16 — Studio MPA provenance tags:** Both the generic Studio MPA deployment path and managed one-click creation write `veadk:agent-type=mpa`, `veadk:managed=true`, `veadk:provisioner=studio-mpa`, trusted `veadk:owner`, and the owned `veadk:mpa-instance-id`. Missing trusted owner fails before cloud mutation, and the raw owner must hash to the task owner before child startup. The one-click route hashes this owner for local task and native registry ownership while passing the raw trusted owner ephemerally to the fixed child process for the Runtime tag; it is not persisted in task state. The shared provisioning service emits Studio provenance only when that route explicitly supplies the trusted Runtime owner, so `veadk mpa create` remains outside Studio discovery. Reconciliation replaces these owned keys, preserves unrelated non-system tags, and never replays `sys:*` tags. A legacy pending create with a persisted pre-provenance request hash replays the exact old create payload and client token, then applies the current provenance tags through the normal Runtime update before completing. Shared constants live in an internal MPA tag module and do not add a public Python API. Tags are discovery metadata, not authorization. Existing managed one-click Runtimes without `veadk:managed=true` require an explicit supported update/retry or future backfill before Studio lists them. Implemented and locally verified on 2026-09-29 by [Studio-created MPA Runtime filtering](../../prd-spec/features/studio-mpa-source-filter/2026-09-28-studio-mpa-source-filter.md); real-browser discovery remains a separate local acceptance step.

- **CON-1 — configuration:** Studio uses a code-owned Beijing profile and ignores `VEADK_MPA_CREATE_CONFIG`; its non-account Runtime settings retain the former private defaults; Studio image defaults use the two latest references in CON-9; the deployment account comes from verified STS identity; VPC/subnet/APIG IDs are not pinned. After automatic PG preparation, Studio resolves shared resources from `mpa_admin_workspace/mpa_admin_db` by verified account and region: validate/reuse registered resources, or create and persist missing VPC/subnet and APIG/IM Gateway through the existing locked provisioners. Existing records are never reset to bypass quotas. Explicit CLI adoption remains supported. See the [registry-owned network fix](../../prd-spec/bugfixes/mpa-shared-network-bootstrap/2026-09-28-registry-owned-network.md). Deployment credentials remain server-side requirements; the model key is discovered under CON-16, never a source literal. The child receives a built-in-profile marker and validates the same profile. CLI `--config` still accepts private YAML with `managed.version: 1`, kebab/snake aliases and unknown-key rejection. CLI `from-runtime` and `template-file` remain mutually exclusive; otherwise flat image/model/PG fields supply the template. CLI `database-admin-url-env` and `shared-database-url-env` resolve PostgreSQL URLs server-side; files/templates are limited to 256 KiB. HTTP clients cannot choose paths, commands, accounts or deployment/PG credentials; CON-11 allows a per-creation OpenViking API Key. Configuration checks are local; they do not prove live access. See [built-in profile design](../../prd-spec/features/mpa-agent-oneclick-provision/2026-09-23-studio-builtin-mpa-profile.md).
- **CON-2 — preparation:** Operators supply PostgreSQL instance/registry/login/owner, IAM roles, images, model access and network connectivity. Verify cloud account and database permissions before preparing account VPC/subnet, APIG/IM Gateway, worker, isolated business database, Skill Space and Runtime. Explicit APIG adoption requires a configured matching VPC. Never assume a newly created VPC reaches private PostgreSQL. Release account locks before waiting for application readiness.
- **CON-3 — identity:** Durable identity is verified account + region + stable agent ID. Native ownership markers, hashes, client tokens and session advisory locks govern reuse. Reject unrelated same-name resources and conflicting unfinished configuration. Persist `studio_owner` in the native deployment record; other owners and preexisting records without this owner cannot take over implicitly. CLI uses owner `cli`; Studio uses the hash of its authorized principal.
- **CON-4 — initialization:** Use real Runtime metadata and shared APIG bootstrap, not legacy placeholder endpoint seeding. Require public/private networking, KeyAuth, MPA tags, bound worker/Skill Space and metadata/IM startup. Reference Runtime templates remove source identity, channel credentials, Skill Space and worker identity. Success requires platform Ready and application `/readiness`.
- **CON-5 — authorization:** All four routes invoke Studio agent-management authorization before configuration/state access. Authenticated ordinary users cannot create; local development retains existing `local` principal semantics. Lookup/cancel is owner-scoped. Duplicate owner/request IDs reuse the task; altered inputs return 409. At most four active tasks globally and one per owner.
- **CON-6 — lifecycle:** States are `running`, `cancelling`, `succeeded`, `failed`, `cancelled`. Start/resume enters `running`; explicit cancellation enters `cancelling`, then `cancelled`; timeout/failure enters `failed`. Successful tasks do not rerun. Stages are `queued`, `checking`, `network`, `gateway`, `worker`, `database`, `skills`, `deploying`, `verifying`; stage is the last observed progress, not a second state machine. Dead supervisors are reconciled on task lookup/start. Recovery retains the original request and agent ID.
- **CON-7 — cancellation:** Run a fixed child module using the current VeADK interpreter. Cancel, deadline or server shutdown terminates the child, waits up to 3 seconds, then kills/reaps it before reporting terminal state. Default deadline is 1800 seconds (60–7200). Persistent cloud resources are retained, including unknown in-flight outcomes. Cancellation is not rollback; retry uses registered intent/token. This flow creates no temporary debugging Runtime to delete.
- **CON-8 — data/security:** Built-in Studio uses `/tmp/veadk-studio/mpa-creation.sqlite3` (server override `VEADK_MPA_TASK_DB`) to persist hashed owner, nonsecret input, state/stage, safe results and supervisor PID, with mode 0600. This is an explicitly temporary, instance-local workaround for read-only cloud code directories: restart may lose history and multiple instances must not rely on shared task limits or locks. Standalone callers retain the `.adk/mpa-creation.sqlite3` convention when they construct the service explicitly. Connections close after each operation. No automatic history expiration. Native PostgreSQL tables remain `mpa_account_network`, `mpa_account_apig`, `mpa_agent_deployment`; require direct/session pooling. STS files are reread; Runtime/network/APIG/worker share account-verified credentials. Protocol messages are bounded to 16 KiB and allowlisted. Never forward raw child output, SDK errors, environment dumps, database URLs or Runtime keys. See the [temporary writable-state fix](../../prd-spec/bugfixes/studio-mpa-writable-state/2026-09-23-use-temporary-state.md).
- **CON-9 — UI:** The MPA filter on Volcengine shows a create card with agent-management permission, including empty lists. The dialog displays fixed region, required Runtime name, description and resource plan; agent ID is server-generated; MPA/Worker image inputs are omitted, as on main; the server uses main’s local latest defaults. Three steps cover basics, automatic PostgreSQL preparation and OpenViking; only step three submits. Persist request identity before POST; lock submitted inputs to make lost-response retry safe. Abort polling on unmount, ignore late responses, preserve server work and recover from session storage on reopen. A confirmed failed or cancelled task offers both same-ID retry and an explicit new-agent action. The latter replaces only the browser draft with a fresh request UUID, blank name and defaults; the server derives the agent ID on submission; it does not delete or mutate the old server task or resources. Running and uncertain-submission states cannot start a different identity from this dialog. Refresh the original region after success. Reuse localized BaseUI/Studio components, keyboard/IME behavior and semantic theme tokens. `ModalLayout.footer` is an optional React node: omitted preserves existing actions, `null` omits the footer; existing callers are unchanged. See [terminal-task new-agent fix](../../prd-spec/bugfixes/studio-mpa-creation/2026-09-24-start-another-agent-after-failure.md).


Invalid Runtime names use a danger-colored border and error text with an accessible alert; the input offers a localized valid-name example. The shared Button primitive visibly dims native disabled buttons and uses a not-allowed cursor, while retaining its loading treatment. Correcting the name restores forward navigation.

## HTTP contract

### Named creation (2026-10-09)

The [named creation design](../../prd-spec/features/mpa-agent-oneclick-provision/2026-10-09-named-studio-creation.md) implements amendments to CON-1, CON-3, CON-5, CON-6 and CON-9.

New Studio forms submit `name`, `requestId`, `description` and `region` plus the existing resource fields; they omit `agentId`, `runtimeImage` and `workerImage`. Name is trimmed and must contain 4–64 ASCII letters, digits, underscores or hyphens. The server derives a stable `mi-[0-9a-f]{24}` agent ID from the trusted owner and request UUID, stores it in the task payload, and retains it across retries. Name participates in request equality and the Runtime creation hash, becomes the new Runtime `Name`, and never replaces `MPA_AGENT_ID` or other resource identity keys. Existing registered Runtime names remain unchanged.

The built-in Studio defaults become `agentkit-platform-2112682748-cn-beijing.cr.volces.com/mpa/mpa_agent:latest` and `agentkit-platform-2112682748-cn-beijing.cr.volces.com/mpa/mpa_codex_worker:latest`. New drafts do not recover hidden old image overrides; submitted drafts/tasks retain their original inputs and image selections. Legacy API requests with explicit `agentId` and optional image fields remain supported, and requests without Name retain ID-based Runtime naming. CLI/YAML overrides remain unchanged. The dialog displays Name and Description without ID/image inputs; invalid names block forward navigation and submission. Existing task authorization, cancellation, concurrency, secret handling and error status semantics remain in force.

Verification maps to route/task/runner/service/runtime/profile tests and dialog/browser tests in the linked design. Cloud creation remains separately verified; new image defaults do not update running agents.

CON-9 navigation correction (2026-09-30): step headings are keyboard-accessible
buttons. Earlier steps and Previous remain available after restoring a submitted
draft; submitted fields stay locked and retry keeps the same identity. Forward
navigation validates image references and the PG target. Busy actions disable
navigation. See [navigation fix](../../prd-spec/bugfixes/mpa-create-navigation/2026-09-30-recover-step-navigation.md).

CON-9 explicit-new-request amendment (2026-09-30, implemented): any submitted draft
offers New Agent, including running/uncertain/unavailable tasks. This explicitly
replaces the browser recovery draft with fresh identity and editable defaults,
without cancelling or modifying the old cloud task. Pending UI actions and config
loads disable it; server admission limits remain unchanged. This supersedes the
terminal-only restriction above. See [design](../../prd-spec/bugfixes/mpa-create-navigation/2026-09-30-explicit-new-request.md).

| Method and path | Response |
| --- | --- |
| `GET /web/mpa-creation/config?region=...` | 200 `{configured,region,error?}`; success also returns safe `source`, resource names, `checks:["configuration"]`, `requiresLiveChecks:true` |
| `POST /web/mpa-creation/tasks` | 202 task snapshot; starts or resumes |
| `GET /web/mpa-creation/tasks/{id}` | 200 owner-scoped task snapshot |
| `POST /web/mpa-creation/tasks/{id}/cancel` | 200 task snapshot; terminal tasks unchanged |

POST body (maximum 8192 bytes, unknown fields rejected):

```json
{"requestId":"11111111-1111-4111-8111-111111111111","name":"customer-service","description":"Customer service","region":"cn-beijing"}
```

`requestId` is a UUID; `name` is required for new requests as specified above; legacy `agentId` matches `[a-z0-9][a-z0-9_-]{0,63}`; `description` defaults to empty, maximum 512 characters; region matches `cn-[a-z]+`, maximum 32 characters. A snapshot contains those fields plus `taskId`, `state`, `stage`, `result`, `error`. Successful result has exactly `runtime_id`, `skill_space_id`, `gateway_id`, `agent_id`, `region`, `state:"ready"`; all are bounded identifiers. No endpoint or credentials are returned. Errors include safe codes `creationFailed`, `timeout`, `interrupted`, `cancelled`. HTTP errors: 400 configuration, 413 body size, 422 invalid input, 409 conflict/capacity, 404 unknown/other-owner task; authorization uses existing Studio status codes. Unsupported provider configuration is unavailable.

## Compatibility, verification and change record

The approved 2026-09-20 migration owns cloud provisioning code and tests in VeADK. No external deployment command or dependency on a provider checkout is supported. API/image/shared-table compatibility changes require review of this contract. Existing CLI behavior and unrelated SDK/harness contracts remain unchanged. Flat-mode supported fields and retry instructions are defined in the operator guide.

CON-1–4 map to configuration/service/network/gateway/worker/database/Runtime tests. CON-5–8 map to route/task tests (ownership, duplicates, lost results, dead supervisors, timeout/reaping, redaction). CON-9 maps to dialog tests, existing directory tests and real-browser checks. CON-13 execution-role permissions map to `tests/cli/test_frontend_deploy_iam.py`; live cloud smoke remains required. Run `uv run --extra dev pytest tests/integrations/mpa_managed tests/cli/test_cli_mpa.py`, frontend test/build/asset gates, changed-file Ruff/Pyright and isolated browser checks. Actual outcomes and remaining baseline/environment limitations are recorded in the design. Simulated tests and a browser with fake APIs do not prove live cloud deployment; cloud smoke is separately authorized.

Studio configuration failures identify missing server environment credentials or an unsupported region without revealing values. CLI YAML profiles still distinguish absent/unreadable files, invalid YAML and absent/invalid Runtime JSON templates; errors identify the relevant setting without returning private paths, file contents or parser exception details. This preserves CON-1/CON-8 and the existing HTTP shape.

Worker discovery follows the provider's `NextToken` cursor with `MaxResults=100`; page length does not determine completion. Repeated cursors and more than 1,000 pages fail explicitly. Matching ToolIds are deduplicated across overlapping pages, while distinct same-name resources remain ownership collisions. Failed or incomplete discovery must never be treated as resource absence (CON-2/CON-3).

CON-3 naming: fresh managed Runtime `Name` equals `MPA_AGENT_ID`. Existing registered Runtime names are preserved. A pending legacy create without a returned Runtime ID retains its hashed name only when the complete legacy payload matches the persisted request hash, preserving ClientToken retry semantics. Other input changes remain conflicts. Runtime IDs and database/worker/Skill Space identities are unchanged. The current UpdateRuntime API does not expose Name, so this does not rename existing cloud instances.

CON-1 image precedence: optional `managed.runtime.image` explicitly selects a custom MPA image (ArtifactType `image`) over the chosen reference/template/flat source. Omission/null preserves source behavior. Empty, whitespace-containing, placeholder values and unknown runtime keys fail local validation. It can supply the required image in flat mode, without replacing other prerequisites. `managed.worker.image` remains independent. No automatic update of existing agents or relaxation of pending-request hash checks occurs.

CON-1 explicit infrastructure: `managed.runtime` optionally accepts `role-name`, positive `cpu-milli`/`memory-mb`/`max-concurrency`, nonnegative `min-instance`, positive `max-instance`, `apmplus-enable`, `project-name`, and `env` (string environment values, whole `${ENV_NAME}` references resolved server-side). Explicit values override reference/template/flat settings; omitted fields preserve defaults. Validate min<=max after merging the source. Flat `model-*` and `pg-*` plus `managed.network.vpc-id/subnet-ids` permit reference-independent configuration. Runtime env keys must be uppercase environment identifiers; provisioning-owned agent/runtime/tool/skill IDs, derived database name, runtime endpoint/auth/encryption, database-admin/shared-registry URLs and request/telemetry identities are rejected. CON-3/CON-8 generation, secret redaction and pending request consistency remain authoritative. Worker reference settings are independent of the MPA Runtime source.

CON-9 creation images: New forms have no image inputs and use the built-in latest defaults. Only legacy requests and already-submitted drafts retain explicit images; submitted fields stay locked. POST accepts optional trimmed image references (max 1024 characters), rejects URLs/credentials/query fragments/invalid SHA256 digests, and never treats them as shell commands. Config exposes only locally available image defaults; reference-only defaults may remain empty. CON-6/CON-8 task storage adds an `images` JSON column with `{}` for legacy rows. First submission snapshots locally resolved effective images; retries reuse that column and reject changes to explicit inputs. Task responses include this nonsecret snapshot, and the fixed runner applies it to a copied profile. Explicit worker images clear a configured existing-worker selection for this new task. Authorization and all other resource settings remain server-owned.


CON-10 — worker recovery/diagnostics: transient Worker operations have at most 4 attempts with 1/2/4-second waits, within a default 600-second stage budget and the task deadline. Create retries retain the same payload/ClientToken; recognized not-found is recoverable only for a registered managed worker. Permanent/unknown errors and ownership conflicts fail immediately. Safe enum-only diagnostics are logged and stored in `task_diagnostics` (latest 100 per task, retained across retries); raw exception data is never persisted. Task HTTP fields and error codes are unchanged. See [approved design](../../prd-spec/bugfixes/mpa-worker-retry/2026-09-20-worker-retry.md).

CON-10 metadata visibility: distinguish absent initialization metadata from explicit conflicts. A managed Worker with persisted ID/token/hash may wait for missing ID/project/ownership tags only in Creating/Pending/Starting/Initializing/Provisioning or absent status, polling every 5 seconds within the existing Worker/task deadline, without an independent observation limit. Ready with missing metadata, present conflicts, terminal/unknown states and workers without managed creation intent fail immediately. Fixed field diagnostics never include values; metadata attempts saturate at 4 to preserve the diagnostic protocol. Worker API error retry limits remain unchanged. See [deadline correction and verification limits](../../prd-spec/bugfixes/mpa-worker-retry/2026-09-30-worker-metadata-deadline.md).

## Proposed automatic PG granularity (not implemented)

This historical proposal is superseded for the current flow by **CON-12 / CON-13** below: shared management/business Workspaces, with database-level business isolation and optional automatic preparation.

The [deployment-account PG design](../../prd-spec/features/mpa-serverless-pg/2026-09-21-deployment-account-pg.md) follows ArkClaw’s per-agent business Workspace granularity. Identity is deployment account + region + stable agent ID; same-agent retry reuses its Workspace, while another agent receives a different one. All PG calls use VeADK deployment credentials, not ArkClaw resource-account delegation. Existing-PG mode and active contracts above remain unchanged. Independent shared-registry bootstrap/resource count and the detailed design require approval before implementation; a business Workspace must never implicitly become the shared management registry.

## Three-step creation inputs

**CON-11 — prerequisites:** See [three-step creation design](../../prd-spec/features/mpa-agent-oneclick-provision/2026-09-23-studio-mpa-three-step-creation.md) and [OpenViking credential extension](../../prd-spec/features/mpa-agent-oneclick-provision/2026-09-23-studio-mpa-openviking-key.md). Authorized config inspection additionally returns nonsecret `pgHost` and `pgPort` from the administrator URL. POST optionally accepts `pgHost`, `pgPort`, `openvikingUrl` and `openvikingResourceId`; the fields are nonsecret and limited to 255, 5, 1024 and 128 characters respectively. PostgreSQL host and port must be provided together and match the configured administrator connection before provisioning. The OpenViking URL must be HTTPS, without embedded credentials, port, query or fragment; all three OpenViking fields (URL, resource ID and API Key) are required together; the resource ID matches `ov-[a-zA-Z0-9_-]+`. Nonempty nonsecret choices are retained with the task. When all three OpenViking fields are blank, the new Runtime has no `OPENVIKING_*` variables even if its source template/reference has them. POST also accepts an optional `openvikingApiKey` of at most 512 characters. The masked key stays in browser memory, enters the authorized POST and child process stdin, is injected only for this creation together with URL, resource ID and `OPENVIKING_USER=default`, and is never returned by task endpoints or stored in session storage/SQLite. A failed retry after browser/server restart requires the key to be entered again. PostgreSQL password remains server-owned. The Studio creation flow injects `OPENVIKING_USER=default` only when OpenViking is enabled. The legacy CLI keeps its own profile settings. The console links are navigation aids, not service endpoints or resource provisioning. The legacy CLI is unaffected; Studio requests with blank OpenViking fields create Runtimes without OpenViking variables.

## Two PostgreSQL Workspaces

The config response adds optional `postgresLayout: "split-workspaces"`, `adminWorkspaceName: "mpa_admin_workspace"` and `adminDatabaseName: "mpa_admin_db"`. Workspace IDs and maintenance URLs are not returned. The copy command rejects `pending=true` Runtime deployments until they are reconciled under the original configuration; persisted request hashes are never rewritten by migration.

**CON-12 — separated registry (manual mode; automatic mode is defined in CON-13):** Optional `managed.postgres` selects the [two-Workspace contract](../../prd-spec/features/mpa-space-scoped-resources/2026-09-23-two-pg-workspaces.md). The manually created management Workspace is named `mpa_admin_workspace`, with shared tables in `mpa_admin_db`. A separate business Workspace retains one `mpa_agent_<hash>` database per agent. Distinct configured Workspace IDs and connection targets are validated locally; operators verify their cloud ownership. Existing account/region APIG/network keys and Runtime bootstrap wire format are preserved. The separate management maintenance credential is used only by `veadk mpa init-admin-db`; normal creation uses the existing management database. Optional migration via `--source-url-env` copies only the three registry tables, retains the source, rejects target conflicts/extras, and requires a coordinated writer outage and Runtime URL cutover. Deployment records pin Workspace IDs. No automatic business migration or Workspace deletion occurs. Legacy profiles remain supported. Implementation/evidence status is recorded in the linked design.

## CON-13: Automatic shared PostgreSQL Workspaces

`managed.postgres.mode: auto` opts into deployment-STS-backed AIDAP preparation. Configuration inspection is read-only and needs no PG credentials; it returns `postgresMode: "auto"` and empty `pgHost`/`pgPort`. The PG wizard step explains preparation; POST rejects nonempty PG host/port fields. Unsubmitted drafts clear old PG targets; submitted payloads remain unchanged and incompatible retries are blocked. OpenViking configuration remains the third step. The Studio execution role must cover caller identity, all VPC/subnet discovery and creation performed by `NetworkCloud`, all APIG/IM Gateway operations performed by `GatewayCloud`, the nine explicit AIDAP operations performed by `PGCloud`, and AgentKit Worker, Skill Space, and Runtime operations. The default role grants the [audited explicit cloud set](../../prd-spec/bugfixes/studio-mpa-aidap-permissions/2026-09-23-complete-mpa-cloud-runtime-policy.md) plus its existing `agentkit:*` coverage and is refreshed during `studio update`; customer-owned roles remain operator-managed.

For each verified account/region/project, prepare `mpa_admin_workspace/mpa_admin_db` and one `mpa_business_workspace` (business name configurable). Each MPA retains its independent business database. AIDAP Workspace IDs are resolved/validated against account, region, project, name, engine and ownership tags. Optional explicit IDs adopt existing Workspaces. Legacy/manual mode is unchanged. New task stages are `admin_workspace`, `business_workspace`, `admin_database`.

Store nonsecret intent and resource identity in a private SQLite bootstrap file. The built-in Studio profile temporarily uses `/tmp/veadk-studio/mpa-pg-bootstrap.sqlite3` so cloud creation does not write to its read-only code directory; standalone YAML retains `.adk/mpa-pg-bootstrap.sqlite3` unless configured otherwise. All creation processes on one instance must share this state path and its OS locks. The Studio `/tmp` path is not durable across instance replacement and is not shared by independent hosts; after state loss, inspect cloud resources before retrying an uncertain create. Persist intent before CreateWorkspace and ID before readiness waits. Never blindly retry uncertain creation; discover by scope/tags or adopt by ID. Definite authorization/parameter rejections can retry after correction. Preserve resources on cancellation, timeout and downstream failure; never replace a deleted recorded Workspace. Provider errors are sanitized; credentials are refreshed and account-checked per SDK call, used only server-side, and never returned by config/tasks or written to bootstrap state.

For a recorded Workspace created by this bootstrap, temporarily missing detail fields, expected ownership tags, or provider not-found responses are readiness states within the existing timeout. A present conflicting identity or ownership value fails immediately. Explicitly adopted Workspaces retain strict validation. Retrying an owned Workspace never issues another CreateWorkspace call.

A configured legacy registry URL blocks automatic provisioning by default. Explicit `managed.postgres.legacy-urls: ignore` opts new creations into fresh admin and business Workspaces; both old PG environment URLs are ignored for this profile. Existing agents and databases are not migrated, modified or deleted. Alternatively, `init-admin-db --source-url-env ...` prepares the new management database and atomically copies the stopped source registry. Existing business data requires an explicit business Workspace ID and unchanged endpoint. Only after coordinated writer/Runtime cutover may operators clear old registry URLs and enable migrated creation. This operation does not move existing business databases or repoint running Runtime environments. See [design and verification](../../prd-spec/features/mpa-space-scoped-resources/2026-09-23-auto-pg-workspaces.md).

## CON-14: Runtime registry URL compatibility

Managed creation translates `sslmode` to the asyncpg `ssl` query parameter in the Runtime's `SHARED_APIG_DATABASE_URL`, retaining the configured TLS mode and all other connection fields. Compatible URLs remain unchanged; conflicting or repeated TLS parameters fail without exposing credentials. Initial creation and finalization use this representation. Pending hashes differing only by this conversion may resume; an unknown Runtime ID still requires exact replay of the original create payload and client token before normalized finalization. Other input changes remain rejected. See [fix and verification](../../prd-spec/bugfixes/2026-09-23-mpa-registry-tls-url.md).

### Managed sandbox template naming (CON-3)

New named Studio requests use the entered, validated Runtime name unchanged as the sandbox template Name (4–64 ASCII letters, digits, hyphens or underscores). Legacy CLI requests without a name still use the trimmed agent ID with `-` replaced by `_`. Internal agent IDs, database/Skill Space/channel identities, scoped ownership tags and Runtime ToolId bindings are unchanged. Existing worker IDs are authoritative and are never renamed. New pending intents persist `worker_name` in deployment JSON and reject later name changes. Older pending intents without that field replay a normalized-ID or hashed name only when the complete candidate payload matches the persisted worker_hash, preserving ClientToken. Other payload changes and unrelated same-name resources remain errors. See [named Worker design](../../prd-spec/bugfixes/mpa-worker-naming/2026-10-09-runtime-named-worker.md).

## Managed MCP signing secret

Every managed MPA Runtime receives `MCP_TOKEN_SECRET`. Explicit nonblank template environment values take precedence over the target Runtime's value, which takes precedence over the agent-owned PostgreSQL `mpa_deployment_settings` entry `mcp_token_secret`. If all are absent, generate 32 random bytes as 64 hex characters and persist before cloud creation. Atomic insert-or-retain keeps uncertain-create retries stable. Reconcile an explicit/current value only after validating the pending request hash, so rejected changed retries cannot corrupt the original request. Database failures stop creation and dispose connections. Reference Runtime templates exclude the source Agent's key; explicit JSON templates may configure one. Finalization retains the key; normal results and the shared nonsecret deployment registry exclude it. No frontend fields or automatic existing-deployment migration are added. See the [bilingual design](../../prd-spec/bugfixes/mpa-runtime-mcp-secret/2026-10-07-persistent-mcp-secret.md).

## Managed Runtime IAM role

Built-in Studio sets `managed.iam.mode: auto`; explicit profiles default to `existing`. Auto preparation runs after STS account validation and before workload identity or other resource mutations. Only a fresh default `IDRoleForArkClawShareAgent` configuration is supported. IAM is account-scoped. Get/create role and `VeADKMPARuntimeAccessV1`, validate account/name and unconditional trust in `vefaas` and `apig`, add missing Global bindings for the approved 12 system policies and 14 custom actions, then verify readback. ## CON-16: Deployment-account Ark model key

Defined by [account-key design](../../prd-spec/features/mpa-model-key-discovery/2026-10-10-account-ark-key.md): built-in Studio selects `managed.model-key.mode: ark`, with optional exact ID/name selectors (`VEADK_MPA_ARK_API_KEY_ID` / `VEADK_MPA_ARK_API_KEY_NAME`). Local inspection requires no raw model key or cloud access. Creation uses refreshed, STS-account-checked deployment credentials for ListApiKeys/GetRawApiKey before resource mutations. Read all pages and deduplicate IDs. Exact selectors require one match; otherwise multiple eligible keys select the newest creation instant, with lexicographically greatest string ID for ties. Accept CreateTime (CreatedAt/CreationTime compatibility), positive Unix seconds/milliseconds or timezone-qualified ISO 8601; missing/invalid time on any eligible candidate fails before raw lookup. A sole candidate needs no timestamp. Reject explicit non-Active states and support legacy missing Status. See the [newest-key successor](../../prd-spec/features/mpa-model-key-discovery/2026-10-10-latest-created-key.md). Never use masked values or create keys. The copied profile injects the raw key into Runtime only; provider text and credentials stay out of events, logs and task/bootstrap storage. Calls have bounded timeouts and at most three transient attempts; cancellation prevents subsequent mutations. Existing hash checks reject changed pending payloads. CLI defaults to explicit keys; general Agent auth is unchanged. Existing deployment roles already grant the two Ark actions; customer-owned roles need permission. Model activation/access and key IP rules remain operator prerequisites.
