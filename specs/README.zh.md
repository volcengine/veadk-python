# 组件规格规范

[English](README.md)

本目录存放 VeADK 持续维护的组件契约。组件 spec 说明组件负责什么、对外提供什么，以及实现和调用方必须保持哪些不变量。它不是变更提案、实施日志，也不是源码的复制品。

## 1. 与其他文档的关系

- [AGENTS.md](../AGENTS.md) 使用英文定义仓库级开发流程和门禁。
- [prd-spec/](../prd-spec/README.zh.md) 描述具体变更、备选方案、实施任务和验收证据。
- `specs/<component>/` 定义组件持续维护的职责和行为契约。
- [frontend/SPEC.md](../frontend/SPEC.md) 继续作为 Studio 前端及配套后端开发规范。组件 spec 引用它，不重新定义视觉、交互或编码规则。
- 用户文档和示例说明如何使用产品。契约变化影响用户时应同步更新，组件 spec 不能代替它们。

每个契约只有一个归属方。调用方 spec 引用归属方契约并说明自身义务，而不是复制协议。实现是当前行为的证据，不是静默改变已批准契约的依据；发现不一致时应明确报告和解决。

## 2. 目录结构与命名

```text
specs/
├── README.md
├── README.zh.md
└── <component>/
    ├── README.md
    └── README.zh.md
```

- 根据职责使用稳定的英文 kebab-case 组件名，不使用版本、日期、任务或单个源码文件作为命名依据。
- 英文为 `README.md`，中文为 `README.zh.md`。两份文件描述同一组件的同一修订。
- 实际变更或明确的文档任务需要时再创建组件目录。不预填推测性契约，也不声称尚无文档的组件已具备 spec。
- 组件 spec 原地持续更新，由 Git 历史保留修订；带日期的变更提案放在 `prd-spec/`，不建立多份按日期并行的组件 spec。
- 默认将每个组件的契约保留在一组 README 中。确实过大时，只能按明确职责边界拆分，并提供双语文件和索引；不得机械地为每个 Endpoint 建立文件。

## 3. 双语维护

1. 每份组件 spec 及本目录规范都必须具备完整英文版和中文版，在顶部附近相互链接。
2. 同步组件 ID、修订日期、状态、契约 ID、接口名、字段、状态名、路径、命令、数值限制和示例。翻译解释性正文，不翻译面向程序的标识符。
3. 同一次变更更新两版。任何一版都不得遗漏另一版的约束、错误、风险或兼容要求。
4. 缺少对应版本、翻译过期或相互矛盾会阻塞批准和交付。必须明确消除差异；任一语言版本都不能独立授权相互冲突的实现。
5. 保持 `specs/` 之外的局部文档惯例，尤其不改变文档站中文 `.mdx` 和英文 `.en.mdx` 的配对方式。

## 4. 组件边界选择

根据实际代码归属和运行职责划分边界。以下领域仅作为调查起点，不代表已有组件规格，也不是强制目录清单：

| 领域 | 代表性实现位置 | 应考虑的契约 |
| --- | --- | --- |
| Agent 执行 | `veadk/agent.py`、`veadk/runner.py`、`veadk/agents/` | 公开 SDK 入口、调用、事件产生、委派、取消和错误。 |
| 配置与模型 | `veadk/config.py`、`veadk/configs/`、`veadk/models/` | 配置优先级、校验、Provider 选择、重试和凭据。 |
| 记忆与知识 | `veadk/memory/`、`veadk/knowledgebase/` | Session 身份、持久化、检索、隔离、保留周期和失败行为。 |
| 工具与协议 | `veadk/tools/`、`veadk/toolkits/`、`veadk/a2a/`、`veadk/a2ui/` | 工具契约、发现、协议映射、权限和不可信输入。 |
| 运行时与 Harness | `veadk/runtime/`、`veadk/extensions/harness/`、`veadk/integrations/agentkit/` | 运行时生命周期、Session/流行为、Sidecar 集成、恢复和资源清理。 |
| Studio 与代码生成 | `frontend/src/`、`frontend/server/`、`veadk/cli/` | UI/服务端边界、API 类型、项目生成、部署 Payload 和生成产物。 |
| 可观测性 | `veadk/tracing/` 及相关集成代码 | 日志、Trace、指标、错误诊断和脱敏。 |

定义归属前先核对相关代码、测试和调用方。组件可以跨越多个目录，但 spec 必须解释其职责边界，而不只是列出文件。

## 5. 必需内容

两种语言采用以下提纲。适用章节必须具体；不适用章节说明理由，不得虚构机制。

| 章节 | 必需内容 |
| --- | --- |
| 元信息与范围 | 组件 ID、状态（`draft` 或 `active`）、修订日期、对应语言链接、归属代码、测试、相关 PRD 和依赖组件。 |
| 职责与非目标 | 组件负责什么、委托什么，以及哪些调用方依赖它。 |
| 入口与依赖 | 适用的公开导入、CLI 命令、HTTP 路由、事件、内部接口及外部系统，明确接口两端的归属方。 |
| 契约 | 稳定的 `CON-*` ID、输入输出、字段类型、必填项/默认值、校验、错误和副作用。对外接口提供具体示例。 |
| 状态与并发 | 适用的合法状态和转换、终态行为、顺序、重复/迟到事件、取消、超时、重试/幂等和重启行为。 |
| 数据与配置 | 事实来源、持久化边界、Schema/版本语义、配置优先级、环境变量及默认值。 |
| 安全与隔离 | 认证授权、身份边界、不可信输入、凭据处理、脱敏和允许的外部副作用。 |
| 兼容性与演进 | 支持的调用方/依赖版本、破坏性变更影响、所需调用方更新、必要的迁移或恢复，以及明确的废弃决策。 |
| 可观测性与失败 | 诊断信号、错误传播、失败模式、恢复保证和资源上限行为，不得虚构尚不存在的指标。 |
| 验证 | 契约到测试的映射、反向/边界用例、集成/E2E 要求、可执行的仓库命令及所需环境。 |
| 变更记录 | 相关已批准 PRD、契约变化、实现状态、验证引用和已知限制。 |

新起草的组件 spec 必须区分已观察行为、预期变更和待决问题。`active` 表示文档声明的当前契约已经评审并与实现、测试核对一致，不表示所有未来提案均已实现。

## 6. 何时必须修改 spec

每份功能、重构和 Bug 修复 PRD 都必须评估组件 spec 影响。以下内容发生变化时，应创建或更新 spec：

- 组件职责、依赖方向、公开导入或共享接口。
- HTTP/API/CLI 契约、事件 Schema、错误码、默认值或配置优先级。
- Session/状态转换、流语义、持久化、并发、取消或恢复。
- 认证、权限、凭据处理、信任边界或数据隔离。
- 兼容性保证、生成项目、部署/运行时行为或可观测性契约。

保持以上契约不变的纯实现改动无需修改组件 spec，但应在 PRD 中记录无影响的理由。不得为了交付一个局部变更而补写全仓组件 spec。

## 7. 变更与评审流程

1. 检查组件当前代码、测试、调用方及已有文档，区分已验证行为和假设。
2. 在双语 PRD 中描述拟议变更，并按 ID 列出受影响组件契约。
3. 实现前更新组件 spec 的两种语言。明确标记拟议行为并关联 PRD，避免被误认为已可用行为。
4. 评审 PRD/spec 一致性、职责归属、接口完整性、状态/失败行为、安全、兼容性、可测试性和双语等价性。在实现契约变化前清零阻塞项。
5. 实现并验证已批准变更。每个变化的契约都必须映射到测试或明确验证步骤；跨运行时或 UI 边界时，提供相应集成和端到端证据。
6. 交付前将两版与实际行为对齐，为已实现变化移除过期的提案标记，并关联验证证据。不得把未实现的保证标为 active。

明确的纯 spec 任务可以将已评审提案作为文档交付，但必须保留清晰的拟议标记；文档批准不等于实现证据。

## 8. 验证与完成标准

使用紧凑映射，不重复 PRD 的实施任务清单：

| 契约 | 保证 | 测试或验证 | 证据 |
| --- | --- | --- | --- |
| `CON-1` | 可观察不变量 | 精确测试路径/命令或操作步骤 | 相关 PRD 验证记录或产物 |

- 使用 VeADK 的实际工具及受影响 CI 工作流，不引入不存在的 `make` 目标，也不照搬其他项目的覆盖率阈值。
- 除修改的实现外，还应检查当前调用方。受影响的 SDK 兼容性、生成代码、前端类型、运行时 Payload 和示例必须一致。
- 区分自动化测试、本地模拟集成和真实浏览器/云/Provider 验证，说明每项结果能证明什么、不能证明什么。
- 检查结果记录为 `pass`、`fail`、`blocked`、`not_run` 或 `not_applicable`，后三种说明原因。跳过或未执行的检查不算通过。
- 原始执行日志和重复任务报告不放入长期契约；链接相关证据，仅保留契约层面的结论和限制。
- Spec 和证据中均不得包含真实凭据、签名 URL、个人数据或未脱敏生产日志。
