Tracing records the **full chain** of an agent's execution and is the core of observability in enterprise-grade agent applications. It turns a request's complete flow—user input, model reasoning, tool calls, memory and knowledge-base access, response generation—into analyzable, traceable structured data, providing a basis for debugging, monitoring, and optimization.

## Enabling Observability in VeADK

To enable full-chain observability, attach an `OpentelemetryTracer` with one or more exporters to your agent. The example below uses the APMPlus exporter:

<Tabs items={['Code', 'Required Environment Variables']}>
  <Tab value="Code">
    ```python title="examples/tracing/tracing_exporter.py"
    import asyncio
    from veadk import Agent, Runner
    from veadk.tracing.telemetry.exporters.apmplus_exporter import APMPlusExporter
    from veadk.tracing.telemetry.opentelemetry_tracer import OpentelemetryTracer

    # Initialize the tracing exporter
    exporters = [APMPlusExporter()]
    tracer = OpentelemetryTracer(exporters=exporters)

    # Define the agent and attach the tracer
    agent = Agent(tracers=[tracer])

    runner = Runner(agent=agent)
    response = asyncio.run(runner.run(messages="hi!"))
    print(response)
    ```
  </Tab>
  <Tab value="Required Environment Variables">
    Configure the exporter via environment variables:

    - `OBSERVABILITY_OPENTELEMETRY_APMPLUS_API_KEY`: The API key of the APM service
    - `OBSERVABILITY_OPENTELEMETRY_APMPLUS_ENDPOINT`: The endpoint of the APM service, e.g. `http://apmplus-cn-beijing.volces.com:4317`
    - `OBSERVABILITY_OPENTELEMETRY_APMPLUS_SERVICE_NAME`: The service name for APM, e.g. `python_coder_agent`
    - `OBSERVABILITY_OPENTELEMETRY_TRACE_CONTENT`: Whether to collect Agent, LLM, and tool input/output content, default `true`

    Or define them in `config.yaml`:

    ```yaml title="config.yaml"
    observability:
      opentelemetry:
        trace_content: true
        apmplus:
          endpoint: ...
          api_key: ...
          service_name: ...
    ```
  </Tab>
</Tabs>

## Limit local retention

The following settings ship with this fix and are unavailable in the published 1.1.14 release and earlier versions

`OpentelemetryTracer` retains up to 1024 recent spans with an estimated data budget of 16 MiB by default. It evicts the oldest spans when either limit is reached. A span exceeding the byte limit is skipped locally and still passed to cloud exporters according to the existing configuration

Set these environment variables before starting the application to adjust local retention:

| Environment variable | Type | Default | Description |
| --- | --- | --- | --- |
| `OBSERVABILITY_OPENTELEMETRY_INMEMORY_ENABLED` | Boolean | `true` | Whether to retain local span history |
| `OBSERVABILITY_OPENTELEMETRY_INMEMORY_MAX_SPANS` | Nonnegative integer | `1024` | Maximum retained span count; `0` disables retention |
| `OBSERVABILITY_OPENTELEMETRY_INMEMORY_MAX_BYTES` | Nonnegative integer | `16777216` | Estimated data budget in bytes; `0` disables retention |

For applications that only need cloud observability, set this variable in the terminal used to start the application:

```bash
export OBSERVABILITY_OPENTELEMETRY_INMEMORY_ENABLED=false
```

Disabling local retention preserves span annotations, trace IDs in logs, and configured cloud exports; `tracer.dump()` writes an empty array. With retention enabled, dumps contain only retained session history. If a span used to associate a trace with a session is evicted, that trace may also disappear from local dumps. Query your cloud observability platform for complete history

Tracers using the same TracerProvider share these limits. Configuration takes effect when the cache is first created; restart the application or create a new provider after changing it. The byte budget estimates cached data and does not limit total process memory

## Why Tracing

With tracing in place, you can:

- **Debug and locate problems**: Quickly pinpoint where logic errors, tool-call failures, or abnormal model output occur;
- **Analyze performance**: Discover bottlenecks from per-module latency and optimize model-call and tool-execution strategies;
- **Audit and comply**: Keep a complete record of requests, responses, and decisions;
- **Coordinate multi-agent systems**: Analyze invocation relationships and data flow between agents in collaboration scenarios.

## Tracing Data Structure

Tracing data consists of a series of **spans**, each recording the name, IDs, start/end time, and attributes of one operation (such as calling the model or executing a tool). Below is an example of a single tool-call span:

```json title="tracing.json"

  "span_id": 15420762184471404328,
  "trace_id": 195590910357197178730434145750344919939,
  "start_time": 1762770336065962000,
  "end_time": 1762770336066380000,
  "attributes": {
    "gen_ai.operation.name": "execute_tool",
    "gen_ai.tool.name": "get_city_weather",
    "gen_ai.tool.input": "{\"name\": \"get_city_weather\"}",
```

## Request, model, and first-token timestamps

VeADK's default LiteLLM and Ark Responses adapters add the following extension attributes to model spans when OpenTelemetry tracing is enabled. UTC Unix nanoseconds are used throughout.

| Attribute | Meaning |
| --- | --- |
| `veadk.request.start_time_unix_ns` | HTTP ASGI entry in VeADK AgentKit/Harness apps, or direct VeADK Runner execution entry. |
| `veadk.request.start_source` | `http` or `runner`; an inherited HTTP timestamp takes precedence. |
| `veadk.model.start_time_unix_ns` | Start of one adapter SDK request, not provider inference start. |
| `veadk.model.streaming` | Actual model SDK request mode, independent of HTTP SSE transport. |
| `veadk.model.first_token_time_unix_ns` | Receipt of the first nonempty generated content delta. |
| `veadk.model.first_token_type` | `text`, `reasoning`, or `tool_call`. |
| `veadk.model.first_token_status` | `observed`, `non_streaming`, `no_output`, or `unsupported`. |

First-token capture excludes role/id/signature metadata, empty deltas, usage, heartbeats, and completion-only aggregates. It does not require token usage or content tracing. One chunk may contain several tokens, so this is an SDK-observed first-output timestamp. Non-streaming calls have no first-token timestamp; completion time is never substituted.

Each SDK request creates a `model_request` child span; the owning model span also receives the latest attempt's fields. VeADK-issued retries and fallbacks create separate attempts. Internal LiteLLM/provider retries remain within the observed SDK request (`veadk.model.request_scope=sdk_request`). Unsupported external/custom engines are explicitly marked; invocation span start is not used as model start. Applications outside the VeADK HTTP factories must install the request timing middleware or use VeADK Runner to establish a request timestamp. Client-render timing and TTFT/TPOT histogram reporting are separate capabilities.
